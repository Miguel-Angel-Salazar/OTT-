Paso 00 · Preparación Inicial (Ejecutar antes de iniciar o al abrir el Codespace)

Encender Minikube y Desplegar Toda la Plataforma

Si acabas de abrir el GitHub Codespace (o acabas de encender tu computador), corre este bloque primero para dejar el clúster arriba y con los 3 contenedores corriendo:

# 0. (Solo en GitHub Codespaces la primera vez) Instalar Minikube y dependencias en 10 segundos curl -sLO https://storage.googleapis.com/minikube/releases/latest/minikube-linux-amd64 && sudo install minikube-linux-amd64 /usr/local/bin/minikube && rm -f minikube-linux-amd64 && pip install -q -r backend/requirements.txt pytest # 1. Iniciar el clúster local de Kubernetes usando Docker como motor minikube start --driver=docker # 2. Aplicar los 5 manifiestos de la carpeta k8s/ (Namespace, Secret, Postgres, Backend y Frontend) kubectl apply -f k8s/ # 3. Esperar automáticamente hasta que los 3 Pods estén en estado Ready (1/1 Running) kubectl wait --for=condition=ready pod --all -n ott-platform --timeout=120s
¿Qué hace cada comando por dentro?
  • minikube start --driver=docker: Crea una máquina virtual ligera dentro de Docker con Kubernetes instalado y configura kubectl automáticamente.
  • kubectl apply -f k8s/: Lee los 5 archivos YAML de la carpeta k8s/ en orden (del 01 al 05), descarga las imágenes v1.0.0 desde Docker Hub y crea la base de datos con las 20 películas.
  • kubectl wait ...: Espera hasta que las sondas de salud confirmen que PostgreSQL, Flask y Nginx ya arrancaron por completo.
¿Qué verás en la consola cuando termine?
  • Al terminar minikube start dirá: Done! kubectl is now configured to use "minikube" cluster.
  • Al terminar kubectl wait verás tres líneas que dicen:
    pod/ott-db-0 condition met
    pod/ott-backend-... condition met
    pod/ott-frontend-... condition met

Mostrar el Repositorio Git, Historial de Commits y Carpetas DevOps

git status git branch -a git log --oneline -n 8 ls -la k8s/ .github/workflows/
¿Qué hace cada línea?
  • git status: Muestra que estamos en la rama principal main sin archivos sucios o sin guardar.
  • git branch -a: Muestra las ramas del repositorio (main, docker-integration, frontend).
  • git log --oneline -n 8: Lista los últimos 8 commits con su código identificador (SHA) y mensaje descriptivo.
  • ls -la k8s/ .github/workflows/: Muestra que tanto el pipeline de CI/CD como los 5 manifiestos de Kubernetes están versionados dentro del repositorio.
¿Qué debes señalar en pantalla?
  • Señala los 5 archivos numerados dentro de k8s/ (01-namespace.yaml hasta 05-frontend.yaml).
  • Señala el archivo ci-cd.yml dentro de .github/workflows/.
🎙️ Qué decir en voz alta mientras ejecutas este paso «Empezamos verificando nuestro repositorio en Git. Estamos sobre la rama main sincronizada con GitHub. Aquí observamos el historial de commits y comprobamos que toda la infraestructura como código —tanto el workflow de GitHub Actions en .github/workflows/ci-cd.yml como los cinco manifiestos declarativos de Kubernetes en la carpeta k8s/— se encuentra debidamente versionada junto al código del frontend, backend y base de datos.»
Paso 02 · Lámina 07 de la Presentación

Ejecutar las Pruebas Automatizadas en Vivo y Explicar el Control de Fallos

# 1. Ejecutar las 10 pruebas unitarias (Modelo Movie, bcrypt, filtros por región y rutas HTTP) python -m unittest discover tests -p "test_unit.py" -v # 2. Ejecutar las 4 pruebas de integración directamente dentro del Pod del Backend conectado a PostgreSQL kubectl exec -n ott-platform deploy/ott-backend -- python -c "import urllib.request; print(urllib.request.urlopen('http://localhost:5000/api/health').read().decode())"
¿Qué hace cada comando?
  • python -m unittest discover tests -p "test_unit.py" -v: Corre en vivo las 10 pruebas unitarias con el flag -v (detallado) para que se vea el nombre de cada prueba y la palabra ok al final de cada una.
  • Pestaña Actions en GitHub: Además de la consola, muestra en el navegador la pestaña Actions del repositorio (https://github.com/Miguel-Angel-Salazar/OTT-/actions) donde se ven los 2 Jobs en verde y cómo el Job 2 tiene needs: unit-and-integration-tests.
¿Qué sale en pantalla?
  • Verás listadas las 10 pruebas (`test_password_hashing_and_verification`, `test_filter_by_user_region`, `test_filter_colombian_cinema_case_insensitive`, `test_swagger_docs_accessible`, etc.) seguidas de:
    Ran 10 tests in 0.8s — OK.
🎙️ Qué decir en voz alta mientras ejecutas este paso «Ahora ejecutamos nuestro test runner en vivo. Aquí vemos pasar las 10 pruebas unitarias que validan la creación del modelo Movie, el cifrado de contraseñas con bcrypt, el filtrado regional del catálogo y la disponibilidad de Swagger UI. En GitHub Actions este mismo proceso corre acompañado de un contenedor efímero de PostgreSQL 16 para las pruebas de integración, y si una sola prueba falla, la condición needs más if: success() bloquea automáticamente la construcción de las imágenes Docker.»
Paso 03 · Lámina 08 de la Presentación

Inspeccionar los Dockerfiles y Comprobar las Imágenes en Docker Hub

# 1. Mostrar el Dockerfile del Backend con sus capas, usuario appuser y HEALTHCHECK cat backend/Dockerfile # 2. Mostrar el Dockerfile del Frontend Nginx cat frontend/Dockerfile # 3. Consultar en vivo la API de Docker Hub para ver los tags publicados (v1.0.0, sha, latest) curl -s https://hub.docker.com/v2/repositories/miguelsalazar22/ott-backend/tags | python -m json.tool | grep -E '"name"|"last_updated"'
¿Qué hace cada comando?
  • cat backend/Dockerfile: Imprime en pantalla las instrucciones con las que se construye el contenedor de Flask.
  • cat frontend/Dockerfile: Imprime las instrucciones del contenedor de Nginx (`1.25-alpine`).
  • curl -s https://hub.docker.com/...: Consulta directamente a Docker Hub en internet y muestra que las imágenes están publicadas con etiquetas de versión (v1.0.0), hash de commit (sha-a8b8492, sha-a8898ad) y latest.
Los 4 puntos del Dockerfile que debes señalar
  • 1. Imagen ligera: FROM python:3.11-slim.
  • 2. Orden de capas: Primero COPY requirements.txt . y pip install antes de COPY . . para aprovechar la caché.
  • 3. Seguridad (No-Root): La línea USER appuser para no correr como administrador root.
  • 4. Salud: La línea HEALTHCHECK apuntando a http://localhost:5000/api/health.
🎙️ Qué decir en voz alta mientras ejecutas este paso «En este paso inspeccionamos nuestros Dockerfiles. En el backend destacamos cuatro buenas prácticas: partimos de una imagen ligera python:3.11-slim, copiamos primero requirements.txt para optimizar la caché de capas, creamos y asignamos el usuario sin privilegios appuser para no ejecutar el contenedor como root, e incluimos un HEALTHCHECK hacia /api/health. Además, al consultar Docker Hub verificamos que las imágenes están publicadas con tags identificables: la versión v1.0.0, el SHA del commit y latest.»

Demostrar que no hay Secretos Expuestos y Auditar el Secret en Kubernetes

# 1. Comprobar que el archivo .env está bloqueado por .gitignore git check-ignore -v .env # 2. Listar los ConfigMaps y Secrets creados en el namespace ott-platform kubectl get configmap,secret -n ott-platform # 3. Paso 05 · Lámina 09 de la Presentación

Verificar el Clúster de Minikube y todos los Recursos Desplegados

# 1. Comprobar que Minikube está corriendo y que kubectl apunta al contexto minikube minikube status kubectl config current-context # 2. Mostrar todos los Pods, Services, Deployments, StatefulSet y el Volumen Persistente (PVC) kubectl get pods,svc,deploy,statefulset,pvc -n ott-platform -o wide
Cómo explicar cada bloque que sale en pantalla
  • 1. PODS: Muestra que los 3 pods (ott-db-0, ott-backend-... y ott-frontend-...) dicen 1/1 Running. Ese 1/1 significa que ya pasaron las pruebas de salud (readinessProbe).
  • 2. SERVICES: Señala que ott-db (puerto 5432) y ott-backend (puerto 5000) son de tipo ClusterIP (privados adentro del clúster por seguridad), mientras que ott-frontend es NodePort (80:30080/TCP) para recibir a los usuarios desde el navegador.
Persistencia de la Base de Datos
  • 3. STATEFULSET vs DEPLOYMENT: Señala que Frontend y Backend son deployment.apps (sin estado), pero la base de datos es statefulset.apps/ott-db (con estado).
  • 4. PVC (Volumen Persistente): Señala la última línea: persistentvolumeclaim/postgres-pvc en estado Bound con capacidad de 1Gi. Eso garantiza que los datos de PostgreSQL no se borren si el pod se reinicia.
🎙️ Qué decir en voz alta mientras ejecutas este paso «Verificamos con minikube status y kubectl config current-context que estamos operando sobre el clúster de Minikube. Al listar los recursos del namespace ott-platform observamos los tres pods en estado 1/1 Running: la base de datos PostgreSQL desplegada como StatefulSet con su reclamo de volumen persistente postgres-pvc de 1 Gigabyte en estado Bound; el backend y la base de datos protegidos mediante servicios internos ClusterIP; y únicamente el proxy inverso Nginx expuesto mediante un servicio NodePort.»

🎙️ Qué decir en voz alta mientras ejecutas este paso «Aquí comprobamos la trazabilidad completa de nuestra cadena de entrega: comparamos el commit del repositorio y las imágenes declaradas en los manifiestos de k8s/ con la columna IMAGE e IMAGE_ID de los pods en ejecución dentro de Minikube, confirmando que el clúster ejecuta exactamente la versión v1.0.0 validada por nuestro pipeline.»

Paso 08 · Lámina 12 (En la Segunda Pestaña de Terminal)

Comprobar Error 404 en la API y Consultar la Base de Datos dentro del Pod

# 1. Demostrar caso de error controlado (404 Not Found) al consultar una película inexistente curl -i http://localhost:8090/api/movies/999 # 2. Entrar al Pod de PostgreSQL (ott-db-0) en Minikube y consultar la tabla de favoritos (favorites) kubectl exec -n ott-platform ott-db-0 -- psql -U ott_user -d ott_db -c "SELECT u.email, m.titulo, f.pelicula_id FROM favorites f JOIN users u ON u.id = f.usuario_id JOIN movies m ON m.id = f.pelicula_id;" # 3. Consultar en vivo la tabla watch_history para ver el minuto/segundo guardado por el reproductor kubectl exec -n ott-platform ott-db-0 -- psql -U ott_user -d ott_db -c "SELECT u.email, m.titulo, w.minuto FROM watch_history w JOIN users u ON u.id = w.usuario_id JOIN movies m ON m.id = w.pelicula_id;"
¿Qué hace cada comando?
  • curl -i .../api/movies/999: Pide la película con ID 999 a través del Nginx de Minikube y muestra que el backend responde limpiamente con código HTTP 404 NOT FOUND y el JSON {"error":"Pelicula no encontrada"}.
  • kubectl exec -n ott-platform ott-db-0 -- psql ...: Se mete directamente adentro del contenedor de PostgreSQL que está corriendo en Minikube y hace un SELECT sobre las tablas reales.
¿Por qué este comando vale 14% de la nota (D5)?
  • Porque el Excel pide explícitamente: «Ejecuta escenario completo UI → API → BD → consulta/UI, demuestra persistencia y manejo de al menos un caso de error; sin simulaciones ocultas».
  • Ver la tabla de PostgreSQL respondiendo desde el pod ott-db-0 demuestra al 100% la persistencia real.
🎙️ Qué decir en voz alta mientras ejecutas este paso «Para cerrar la prueba funcional de extremo a extremo, validamos primero en consola el manejo de un error 404 en el endpoint REST pidiendo el ID inexistente 999. Y a continuación ejecutamos kubectl exec directamente contra el pod ott-db-0 de PostgreSQL en Minikube, comprobando con una consulta SQL que los favoritos y el segundo de reproducción de la película están persistidos en las tablas relacionales.»
Paso 09 · Lámina 11 de la Presentación (Cierre de la Demo)

Mostrar Logs, Diagnóstico y Provocar la Caída de un Pod (Self-Healing)

# 1. Ver las últimas 20 líneas de logs del contenedor Flask en Kubernetes kubectl logs -n ott-platform deployment/ott-backend --tail=20 # 2. Mostrar la configuración detallada, sondas Liveness/Readiness y eventos del Deployment kubectl describe deployment ott-backend -n ott-platform # 3. Provocar un incidente en vivo: eliminar el Pod del Backend intencionalmente kubectl delete pod -n ott-platform -l app=ott-backend # 4. Ver cómo Kubernetes ya creó un Pod nuevo automáticamente para reemplazarlo kubectl get pods -n ott-platform -o wide
¿Qué hace cada comando?
  • kubectl logs ...: Muestra las peticiones HTTP que Flask acaba de atender (como el login, `/movie/1` y `/api/health`).
  • kubectl describe deployment ...: Muestra las reglas de CPU/Memoria y las sondas Liveness y Readiness.
  • kubectl delete pod -l app=ott-backend: Destruye a propósito el pod del backend para simular que el servidor se cayó.
  • kubectl get pods -n ott-platform -o wide: Muestra que Kubernetes detectó la caída y en ese mismo segundo creó un pod nuevo (verás que en la columna AGE dice pocos segundos, ej. 5s o 12s).
Qué hacer justo después de borrar el pod
  • Espera unos 10 segundos y vuelve a correr kubectl get pods -n ott-platform para mostrar que el nuevo pod ya pasó de 0/1 a 1/1 Running gracias a que superó la sonda /api/health.
  • Recarga la página en el navegador para mostrar que la plataforma sigue funcionando sin haber perdido ningún dato.
🎙️ Qué decir en voz alta para cerrar la demo «Finalmente, para demostrar observabilidad y respuesta ante incidentes, consultamos con kubectl logs las peticiones procesadas por el backend e inspeccionamos con kubectl describe sus sondas de salud. A continuación provocamos un fallo real eliminando el pod activo del backend con kubectl delete pod: observamos cómo el controlador del Deployment detecta de inmediato que falta una réplica, crea un nuevo pod automáticamente y, tras validar su conectividad con PostgreSQL en /api/health, restablece el servicio en segundos sin pérdida de información.»
