Parte I · Elevator Pitch Criterio P1 · 5%

Problema Real, Destinatarios y Motivación

Expone Integrante 1

🎯 Necesidad del Producto y Usuarios

  • Baja visibilidad del Cine Colombiano e Independiente: Los catálogos comerciales masivos no priorizan curaduría regional latinoamericana.
  • Usuarios Suscriptores: Buscan explorar cine por región (LATAM, EUROPA, USA), guardar su lista de favoritos, calificar títulos y reanudar películas en el segundo exacto.
  • Usuarios Evaluadores / Operación: Necesitan consultar el estado de salud (/api/health) y probar endpoints en vivo con Swagger (/apidocs/).

⚙️ Problema Técnico Inicial que Resolvimos

  • Dependencia de servicios externos cerrados: En la entrega inicial la base de datos dependía de Supabase en la nube.
  • Cuello de botella en un solo proceso: Flask servía tanto las vistas HTML como los archivos de video MP4 pesados, saturando el servidor.
  • Falta de reproducibilidad: Sin contenedores ni pruebas automatizadas en CI, cualquier cambio de código rompía el entorno del equipo.

Propuesta de Valor, Solución y Alcance Real

Expone Integrante 2

✨ Funcionalidades Clave

  • Autenticación segura: Contraseñas cifradas con bcrypt y sesiones firmadas.
  • Catálogo de 20 títulos: Incluye 5 películas colombianas (Monos, El olvido que seremos, La vendedora de rosas, Pájaros de verano, El páramo).
  • Reproductor con memoria: Guarda el segundo de reproducción en PostgreSQL (watch_history).
  • Favoritos, Likes y Búsqueda: Filtros instantáneos y gestión de plan en /profile.

🏛️ Diferenciador Técnico

  • 100% Autónomo y Portátil: Base de datos PostgreSQL 16 propia con inicialización automática (init.sql).
  • Arquitectura Desacoplada en 3 Capas:
    • Frontend: Nginx 1.25 Alpine (Reverse Proxy + Caché).
    • Backend: Python 3.11 + Flask MVC + OpenAPI.
    • Base de Datos: PostgreSQL 16 con volumen persistente.

🚧 Límites Honestos del Alcance

  • Streaming de video: Entrega progresiva de archivos MP4 locales con caché en Nginx (no transcodificación adaptativa HLS).
  • Despliegue declarativo: Manifiestos versionados en Git (k8s/) aplicados sobre Minikube con kubectl apply -f k8s/ (sin operador externo Argo CD ni Jenkins).
Parte I · Elevator Pitch Criterio P3 · 5%

Justificación Técnica y Aporte de las Prácticas DevOps

Expone Integrante 3
Práctica / Decisión Técnica Por qué aporta valor real al producto Compensación (Trade-off) asumida
1. Nginx como Proxy Inverso y Servidor Estático Descarga a Flask de enviar archivos MP4 pesados; aplica caché de 30 días en /static/* y enruta peticiones dinámicas a ott-backend:5000. Añade un contenedor adicional, pero reduce drásticamente la carga de CPU en Python.
2. CI en GitHub Actions con PostgreSQL Real Cada commit levanta un contenedor postgres:16-alpine efímero, carga init.sql y ejecuta 14 pruebas reales antes de construir imágenes. El pipeline toma ~45 segundos adicionales a cambio de detectar errores SQL reales antes del despliegue.
3. StatefulSet + PVC en Kubernetes Garantiza que si el pod de PostgreSQL se reinicia, los usuarios registrados, favoritos y el minuto de reproducción persistan en disco (1Gi). Requiere aprovisionar almacenamiento persistente (postgres-pv / postgres-pvc) en el clúster.
4. Probes HTTP hacia /api/health Kubernetes verifica cada 15 s que Flask y PostgreSQL respondan (SELECT 1) y reinicia el pod automáticamente si falla. Genera una consulta ligera periódica hacia la base de datos.

D2 · CI Automatizada en GitHub Actions, Pruebas y Control de Fallos

Demo en Vivo Integrante 1

✅ Qué Verifica el Pipeline Automáticamente

  • Job 1 (Pruebas con PostgreSQL 16 real):
    • Carga database/init.sql en un contenedor de servicio Postgres.
    • Ejecuta test_unit.py (10 pruebas: modelo Movie, rutas, hashing bcrypt, filtro por región y rutas HTTP).
    • Ejecuta test_flow.py (4 pruebas: /api/health, semillas SQL, login real y navegación autenticada).
  • Control de Fallos: El Job 2 exige needs: unit-and-integration-tests y if: success(). Si falla un test, bloquea el build de imágenes (Run fallido #43124379460 vs Run exitoso #44195742949).

🐳 Buenas Prácticas en los Dockerfiles

  • Caché de capas optimizada: En backend/Dockerfile se copia e instala requirements.txt antes de copiar el resto del código.

Parte II · Demo Técnica Criterio D7 · 5%

D7 · Configuración por Entorno, Seguridad y Secretos

Demo en Vivo Integrante 2

🔐 Protección de Credenciales y Red

  • Archivos sensibles fuera de Git: .env ignorado en .gitignore; plantilla pública en .env.example.
  • Separación en Kubernetes:
    • ConfigMap ott-config: Variables no sensibles (PORT, POSTGRES_DB, BACKEND_URL).
    • Secret ott-secrets: Credenciales codificadas en Base64 (DATABASE_URL, POSTGRES_PASSWORD, SECRET_KEY).
  • Aislamiento de servicios: PostgreSQL (5432) y Backend (5000) usan ClusterIP (solo accesibles dentro del clúster).

💻 Auditar Secretos sin Exponer Contraseñas

D8 · Observabilidad, Logs y Autorrecuperación (Self-Healing)

Demo en Vivo Integrante 3

🩺 Diagnóstico y Respuesta a Incidentes

  • Inspección de logs y estado: Consultamos las trazas HTTP del contenedor Flask con kubectl logs y auditamos las sondas Liveness/Readiness con kubectl describe.
  • Simulación de incidente en vivo: Eliminamos el pod activo de ott-backend.
  • Recuperación automática: El Deployment detecta la caída, crea un pod nuevo inmediatamente y valida /api/health antes de enviarle tráfico.

💻 Comandos de Diagnóstico y Falla Controlada

D6 · Trazabilidad (Commit → CI → Imagen → Manifiesto → Pod)

Demo en Vivo Integrante 4

🔗 Correspondencia Exacta de Extremo a Extremo

  • Commit → CI → Tag: Cada ejecución de GitHub Actions genera una tabla de Trazabilidad en el Job Summary que une el SHA del commit con los tags v1.0.0 y sha-<commit>.
  • Validación CI ↔ Manifiesto: El pipeline verifica con grep que k8s/04-backend.yaml y k8s/05-frontend.yaml usen exactamente el tag v1.0.0.
  • Estado Declarativo en Git: La carpeta k8s/ es la única fuente de verdad del clúster.

💻 Comprobar Trazabilidad en Vivo

git rev-parse --short HEAD Select-String -Path k8s/*.yaml -Pattern "image:" kubectl get pods -n ott-platform -o custom-columns="POD:.metadata.name,STATUS:.status.phase,IMAGE:.spec.containers[*].image,IMAGE_ID:.status.containerStatuses[*].imageID"
