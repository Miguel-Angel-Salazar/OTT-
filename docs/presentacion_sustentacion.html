P1 · Problema Real, Destinatarios y Motivación

Expone (Minuto 0:00 – 1:15)
1. Miguel Ángel Salazar

🎯 Problema de Producto (Dominio OTT)

  • Las plataformas comerciales masivas relegan el Cine Colombiano e Independiente frente a catálogos genéricos sin curaduría regional.
  • Usuarios objetivo:
    • Espectadores / Cinéfilos: Buscan cine curado por región (LATAM, EUROPA, USA), reanudación exacta del minuto de reproducción, lista de favoritos y calificaciones.
    • Evaluadores / Operadores: Requieren auditar salud (/api/health) y probar contratos REST vía Swagger (/apidocs/).

⚙️ Problema de Ingeniería y Configuración

  • En su primera versión, el proyecto dependía de una base de datos externa cerrada (Supabase) y se ejecutaba manualmente en un solo proceso Flask.
  • Consecuencias reales que sufrimos:
    • Falta de reproducibilidad («en mi máquina sí corre»).
    • Flask se bloqueaba al servir archivos de video MP4 pesados y páginas dinámicas en el mismo hilo.
    • Sin pruebas automatizadas en CI, cualquier cambio en SQL o rutas rompía `main` silenciosamente.
🎙️ Frase clave (Miguel): «Nuestra motivación fue doble: ofrecer una plataforma curada con énfasis en Cine Colombiano y transformar un monolito dependiente de terceros en una arquitectura 100% autónoma, reproducible y verificable automáticamente.»

P2 · Propuesta de Valor, Solución y Alcance Real

Expone (Minuto 1:15 – 2:30)
2. Tomás Sepúlveda

✨ Funcionalidades en Producción

  • Autenticación Segura: Registro y login con hashing bcrypt y sesiones firmadas.
  • Catálogo Curado (20 títulos): 5 obras de Cine Colombiano (Monos, El olvido que seremos, La vendedora de rosas, Pájaros de verano, El páramo) con pósters y videos MP4 reales.
  • Reproductor Persistente: Guarda el segundo de reproducción en PostgreSQL (watch_history).
  • Mi Lista, Likes y Búsqueda: Favoritos, ratings y buscador en tiempo real.

🏛️ Diferenciador Arquitectónico

  • 100% Autónomo: Cero dependencia de nubes propietarias; base de datos relacional propia en postgres:16-alpine con 6 tablas y init.sql.
  • Separación en 3 Capas:
    • ott-frontend (Nginx 1.25 Alpine)
    • ott-backend (Flask 3.1.1 + Flasgger)
    • ott-db (PostgreSQL 16 StatefulSet)

🚧 Límites Honestos del Alcance

  • Entrega de Video: Streaming progresivo de archivos MP4 servidos con caché por Nginx (no transcodificación adaptativa HLS).
  • Despliegue K8s: Estado declarativo versionado en Git (k8s/) reconciliado sobre Minikube con kubectl apply -f k8s/ (sin operador externo Argo CD ni Jenkins).
🎙️ Frase clave (Tomás): «El valor concreto de CINÉFILO es que cualquier integrante o evaluador puede clonar el repositorio y levantar las 3 capas con 20 películas funcionales, Swagger interactivo y persistencia real sin depender de ningún servicio externo.»
PARTE I · ELEVATOR PITCH Criterio P3 · Peso: 5%

P3 · Justificación Técnica y Valor de las Prácticas DevOps

Expone (Minuto 2:30 – 3:45)
3. Juan Esteban Vallejo

🔗 ¿Por qué esta Arquitectura y Herramientas?

  • Nginx como Reverse Proxy + Servidor Estático: Descarga a Flask de transferir decenas de megabytes de video MP4. Nginx aplica caché de 30 días en /static/* y solo enruta peticiones dinámicas a http://ott-backend:5000.
  • GitHub Actions con PostgreSQL de Servicio: No hacemos pruebas simuladas en memoria; el pipeline levanta un contenedor postgres:16-alpine real, ejecuta init.sql y corre 14 pruebas de unidad e integración antes de permitir construir imágenes Docker.
  • Kubernetes (Minikube) con StatefulSet + PVC: Mientras Frontend y Backend son stateless (Deployment), PostgreSQL requiere identidad estable y disco persistente (StatefulSet + PersistentVolumeClaim de 1Gi).

⚖️ Decisiones y Compensaciones (Trade-offs)

Decisión TécnicaBeneficio ObtenidoCompensación Asumida
Videos MP4 dentro de la imagen Frontend Portabilidad inmediata sin S3 externo Imagen más pesada (~380 MB), mitigado con caché de capas
init.sql en ConfigMap de K8s Clúster se autoinicializa sin montar carpetas del host Requiere sincronizar el ConfigMap si cambia el esquema
Probes HTTP hacia /api/health Kubernetes detecta si cae la BD y reinicia el pod Ejecuta un SELECT 1 ligero cada 15 segundos
🎙️ Frase clave (Juan Esteban): «Cada práctica DevOps responde a un dolor real del producto: Nginx resuelve el cuello de botella de video, CI con Postgres real evita regresiones SQL, y el StatefulSet con PVC garantiza que el progreso de visualización sobreviva a caídas de pods.»

D2 · CI Automatizada en GitHub Actions, Pruebas y Control de Fallos

Ejecuta en Vivo (3 min)
1. Miguel Ángel Salazar

⚙️ Qué hace .github/workflows/ci-cd.yml

  • Disparadores: push, pull_request a main y workflow_dispatch.
  • Job 1 (CI + PostgreSQL real): Levanta un servicio postgres:16-alpine con healthcheck, inyecta database/init.sql y ejecuta:
    • test_unit.py (10 pruebas: modelo Movie, rutas legacy, hashing bcrypt, filtro regional y endpoints HTTP).
    • test_flow.py (4 pruebas: /api/health contra BD, semillas, login real y sesión).
  • Control de Fallos: El Job 2 exige needs: unit-and-integration-tests + if: success(). Si una sola prueba falla, no se construye ni publica ninguna imagen (evidencia real en Run #43124379460 fallido vs Run #44195742949 exitoso).

💻 Ejecutar Suite de Pruebas en Vivo

# 1. Ejecutar las 10 pruebas unitarias .\.venv\Scripts\python.exe -m unittest discover tests -p "test_unit.py" -v # 2. Ejecutar las 4 pruebas de integración con PostgreSQL .\.venv\Scripts\python.exe -m unittest tests/test_flow.py -v

🔗 Mostrar en navegador: Pestaña Actions de GitHub (Run #44195742949 en verde y Run #43124379460 en rojo demostrando bloqueo).

🎙️ Qué señalar al profesor: «Además de las pruebas de Python, el Job 2 incluye un validador en Python que parsea todos los YAML de k8s/ y verifica con grep que el tag del manifiesto coincida con la versión construida.»

D7 · Configuración por Entorno, Seguridad y Manejo de Secretos

Ejecuta en Vivo (1.5 min)
3. Juan Esteban Vallejo

🔐 Medidas de Seguridad en las 3 Capas

  • Cero archivos .env en Git ni en imágenes: Excluidos en .gitignore y .dockerignore; solo se versiona la plantilla .env.example.
  • Separación ConfigMap vs Secret en Kubernetes:
    • ConfigMap ott-config: Datos no sensibles (PORT=5000, POSTGRES_DB=ott_db, BACKEND_URL).
    • Secret ott-secrets: Credenciales codificadas en Base64 (DATABASE_URL, POSTGRES_PASSWORD, SECRET_KEY).
  • Exposición mínima de red: ott-db (5432) y ott-backend (5000) son ClusterIP (internos al clúster). Solo ott-frontend se expone vía NodePort.

💻 Comprobar Secretos sin Exponer Valores

Cumpliendo la regla de integridad de la rúbrica, inspeccionamos los metadatos sin revelar contraseñas en pantalla:

# Verificar que .env está ignorado por Git git check-ignore -v .env # Inspeccionar ConfigMap y Secret en Kubernetes (valores ocultos) kubectl get cm,secret -n ott-platform kubectl describe secret ott-secrets -n ott-platform
🎙️ Qué señalar al profesor: «kubectl describe secret nos muestra que las 4 llaves existen e inyectan variables de entorno en los pods, ocultando su contenido real en bytes.»

D8 · Observabilidad, Diagnóstico y Autorrecuperación en Vivo

Ejecuta en Vivo (2 min)
4. Sebastián Villa

🩺 Salud, Logs y Prueba de Resiliencia

  • Probes activas: Kubernetes consulta periódicamente GET /api/health:5000 en el backend y pg_isready en la base de datos.
  • Diagnóstico operativo: Con kubectl describe y kubectl logs auditamos las peticiones HTTP recibidas por Flask y los eventos de programación de pods.
  • Incidente provocado en vivo: Eliminamos manualmente el pod activo de ott-backend y observamos cómo el controlador del Deployment levanta un pod nuevo automáticamente en segundos sin perder la sesión ni los datos de PostgreSQL.

💻 Comandos de Diagnóstico y Falla Controlada

# 1. Revisar logs y eventos del backend kubectl logs -n ott-platform deployment/ott-backend --tail=20 kubectl describe deployment ott-backend -n ott-platform # 2. Provocar caída del pod del backend y ver autorrecuperación kubectl delete pod -n ott-platform -l app=ott-backend kubectl get pods -n ott-platform -w
🎙️ Qué señalar al profesor: «Al eliminar el pod, el ReplicaSet detecta que el estado actual (0) difiere del deseado (1), crea un nuevo contenedor y solo le envía tráfico cuando la readinessProbe de /api/health responde 200 OK.»

D6 · Trazabilidad de Entrega (Commit → Imagen → Manifiesto → Pod)

Ejecuta en Vivo (2 min)
2. Tomás Sepúlveda

🔍 Cadena de Trazabilidad Completa

  • 1. Commit en Git: Identificado por su SHA (ej. a8b8492 / a8898ad).
  • 2. Ejecución en GitHub Actions: El Job 2 genera la tabla Summary vinculando el SHA con las imágenes v1.0.0 y sha-a8b8492 y valida que k8s/04-backend.yaml apunte a v1.0.0.
  • 3. Manifiesto → Pod en Minikube: Comprobamos con kubectl get pods exactamente qué imagen e imageID (digest SHA256) está ejecutando el contenedor activo.

💻 Comandos en Vivo para Trazabilidad D6

Comprobar imagen e ImageID exactos en los Pods activos kubectl get pods -n ott-platform -o custom-columns="POD:.metadata.name,STATUS:.status.phase,IMAGE:.spec.containers[*].image,IMAGE_ID:.status.containerStatuses[*].imageID"

D5 · Flujo Funcional E2E Real en Minikube y Casos de Error

Ejecuta en Vivo (3 min)
2. Tomás Sepúlveda

🌐 Recorrido E2E en Vivo (`http://localhost:8090`)

  1. Healthcheck y Swagger: Abrir /api/health (200 OK) y /apidocs/.
  2. Caso de Error 1 (UI): Intentar login en /auth/login con clave errónea → alerta controlada sin caída.
  3. Caso de Error 2 (API 404): Consultar /api/movies/999 → responde JSON 404 Not Found.
  4. Operación Real UI → API → BD: Iniciar sesión con demo@ott.com / demo123, entrar a Monos (/movie/1), alternar + Mi Lista y reproducir el video.
  5. Verificar Persistencia en el Pod ott-db-0: Consultar con psql dentro del contenedor de PostgreSQL en Minikube.

💻 Comandos en Vivo para D5

# 1. Exponer el Service de Nginx (si no está activo) kubectl port-forward svc/ott-frontend -n ott-platform 8090:80 # 2. Demostrar caso de error controlado 404 en la API curl.exe -i http://localhost:8090/api/movies/999 # 3. Verificar persistencia real dentro del Pod PostgreSQL en Minikube kubectl exec -n ott-platform ott-db-0 -- psql -U ott_user -d ott_db -c "SELECT u.email, m.titulo, f.pelicula_id FROM favorites f JOIN users u ON u.id = f.usuario_id JOIN movies m ON m.id = f.pelicula_id;" kubectl exec -n ott-platform ott-db-0 -- psql -U ott_user -d ott_db -c "SELECT u.email, m.titulo, w.minuto FROM watch_history w JOIN users u ON u.id = w.usuario_id JOIN movies m ON m.id = w.pelicula_id;"
🎙️ Qué señalar al profesor: «Todo el tráfico que acabamos de ver en el navegador entró por el Service de Nginx en Minikube, pasó por Flask y quedó grabado en el volumen persistente del StatefulSet de PostgreSQL.»
