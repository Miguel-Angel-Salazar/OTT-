Parte A · Elevator Pitch: Criterio P3 (Justificación Técnica y DevOps · Diapositiva 4)

Qué decir textualmente:
«En el criterio P3 justificamos por qué cada decisión arquitectónica y práctica DevOps aporta valor directo al producto:
• Primero, desacoplar Nginx como Reverse Proxy y servidor de estáticos: Una plataforma de películas maneja archivos de video MP4 pesados. Si Flask sirviera esos videos directamente, bloquearía los hilos de Python para otros usuarios. Al poner a Nginx en el frente (ott-frontend), Nginx entrega directamente /static/videos/* y /static/images/* con cabeceras Cache-Control de 30 días, y solo pasa al backend las peticiones dinámicas.
• Segundo, pruebas contra PostgreSQL real en CI: Muchos proyectos prueban con SQLite en memoria y fallan en producción. Nuestro pipeline levanta postgres:16-alpine en GitHub Actions y prueba el mismo init.sql que usa Kubernetes.
• Tercero, compensaciones asumidas (trade-offs): Incluir los 20 videos MP4 de muestra dentro de la imagen de Frontend incrementa su tamaño a ~380 MB, pero a cambio nos da portabilidad absoluta: cualquier nodo de Kubernetes levanta el catálogo multimedia completo sin requerir credenciales de un bucket S3 externo.»

🗂️ 3. Explicación Completa de Cada Carpeta y Archivo del Proyecto

Para responder cualquier pregunta sobre cómo está construido internamente el software.

1. Carpeta backend/ (API y Servidor MVC Flask)

  • app.py: Punto de entrada de Flask. Configura secret_key, inicializa Flasgger (Swagger 2.0) en la ruta /apidocs/ (especificación JSON en /apispec.json) y registra los 6 Blueprints MVC.
  • config/db_config.py: Carga variables con dotenv y expone get_connection() usando psycopg2.connect(DATABASE_URL, cursor_factory=RealDictCursor).
  • models/movie.py: Clase de dominio Movie con el método de fábrica Movie.from_dict() que normaliza rutas de imágenes (convierte rutas antiguas /static/pictures/ a /static/images/ y asigna hero_url de respaldo).
  • controllers/:
    • api_controller.py: Define GET /api/health (ejecuta SELECT 1 AS test; en PostgreSQL y devuelve 200 o 500), GET /api/movies y GET /api/movies/<id> (devuelve 404 si no existe).
    • auth_controller.py: Rutas /auth/login, /auth/register, /auth/logout y recuperación de contraseña.
    • home_controller.py: Renderiza /home/ filtrando películas por la región del usuario (LATAM, EUROPA, USA o GLOBAL) y arma el carrusel de Cine Colombiano.
    • movie_controller.py: Detalle /movie/<id>, buscador /movie/search?q=..., calificaciones /like y /dislike, y guardado asíncrono POST /movie/<id>/progreso.
    • favorite_controller.py: POST /favorite/toggle/<id> para agregar o quitar de Mi Lista.
    • profile_controller.py: Vista /profile/ para cambiar entre plan Basica y Premium o actualizar contraseña.
  • services/: Contiene toda la lógica SQL parametrizada (previniendo inyección SQL): auth_service.py (usa bcrypt.hashpw y bcrypt.checkpw), movie_service.py, favorite_service.py, rating_service.py, watch_history_service.py y profile_service.py.

❓ 5. Banco de 16 Preguntas Técnicas del Profesor con Respuestas Exactas

Preguntas típicas de defensa clasificadas por integrante para responder con precisión (Criterio D9 · Nivel 4).

Preguntas para Miguel (Arquitectura, Git y CI/CD - D1, D2)

1. ¿Cómo garantizan en GitHub Actions que las pruebas de integración no usen una base de datos simulada (mock)?
En el Job 1 de .github/workflows/ci-cd.yml declaramos un bloque services: postgres:16-alpine con healthcheck pg_isready. Antes de correr los tests, un paso ejecuta psql -h localhost -U ott_user -d ott_db -f database/init.sql, por lo que test_flow.py se ejecuta contra un motor PostgreSQL 16 real con el mismo esquema y semillas de producción.
2. ¿Qué pasa exactamente si un desarrollador sube un commit que rompe el login o borra una ruta?
El paso test_flow.py o test_unit.py devuelve código de salida distinto de cero (falla el Job 1). Como el Job 2 tiene needs: unit-and-integration-tests y if: success(), GitHub Actions cancela automáticamente el Job 2 y bloquea la construcción y publicación de las imágenes Docker.
3. ¿Por qué las 6 pruebas de Playwright no corren dentro del mismo Job 1 de GitHub Actions?
En CI corremos las 10 pruebas unitarias y las 4 de integración HTTP/SQL porque validan toda la lógica y contratos en pocos segundos. Las 6 pruebas E2E de Playwright descargan un navegador Chromium headless completo y las ejecutamos directamente contra el Service expuesto de Minikube (TEST_BASE_URL=http://localhost:8090) para validar el clúster real de extremo a extremo.
4. ¿Qué valida el script de Python que agregaron en el Job 2 del pipeline?
Recorre todos los archivos k8s/*.yaml con yaml.safe_load_all, verifica que cada documento tenga apiVersion y kind válidos, y luego comprueba con grep que el tag de imagen dentro de 04-backend.yaml y 05-frontend.yaml coincida con la variable APP_VERSION del pipeline.

Preguntas para Tomás (Trazabilidad, GitOps y Flujo E2E - D5, D6)

5. ¿Cuál es la diferencia entre CI, CD y GitOps en su proyecto?
CI (Integración Continua) es el proceso en GitHub Actions que ejecuta pruebas y construye las imágenes versionadas ante cada commit. CD / Estado Declarativo es mantener en la carpeta k8s/ de Git la definición exacta del estado deseado del clúster. Aclaramos con honestidad que la reconciliación hacia Minikube la ejecutamos con kubectl apply -f k8s/; para tener GitOps puro automatizado en un clúster cloud bastaría instalar un controlador como Argo CD observando la carpeta k8s/.
6. ¿Cómo sé que el Pod que está corriendo en Minikube corresponde realmente a la versión construida y no a una vieja?
Ejecutamos kubectl get pods -n ott-platform -o custom-columns="POD:.metadata.name,IMAGE:.spec.containers[*].image,ID:.status.containerStatuses[*].imageID". Ahí verificamos tanto el tag declarativo (v1.0.0) como el digest inmutable SHA256 de la imagen cargada.
7. Cuando el usuario ve una película en el navegador, ¿cómo se guarda el minuto de reproducción en la base de datos?
El reproductor JS en el navegador envía periódicamente una petición asíncrona fetch a POST /movie/{id}/progreso con el JSON {"minuto": X}. Nginx la redirige a Flask, el controlador verifica la sesión activa y watch_history_service.py ejecuta un INSERT ... ON CONFLICT (usuario_id, pelicula_id) DO UPDATE SET minuto = EXCLUDED.minuto en PostgreSQL.
8. ¿Qué sucede si la base de datos cae mientras un usuario consulta el catálogo?
En movie_service.py las consultas tienen manejo de excepciones controlado para no exponer trazas internas al usuario, mientras que el endpoint GET /api/health pasa a devolver código 500 con {"database": "disconnected"}, alertando inmediatamente a las sondas de Kubernetes.

Preguntas para Juan Esteban (Docker, Docker Hub y Seguridad - D3, D7)

9. ¿Por qué en backend/Dockerfile copian primero requirements.txt y no hacen COPY . . desde el principio?
Por el mecanismo de caché de capas de Docker. Cada instrucción crea una capa inmutable; si copiamos todo el código primero, cualquier cambio en un archivo HTML o Python invalidaría la caché y obligaría a reinstalar Flask, psycopg2 y bcrypt en cada build. Al copiar requirements.txt primero, la capa de dependencias se reutiliza en segundos.
10. ¿Por qué crearon el usuario appuser en el Dockerfile del backend?
Por principio de mínimo privilegio (seguridad D3 y D7). Por defecto los contenedores corren como root (UID 0); si hubiera una vulnerabilidad en la aplicación, un atacante tendría permisos de superusuario dentro del contenedor. Con USER appuser el proceso Python corre sin privilegios administrativos.
11. ¿Cómo evita Nginx tener la URL del backend quemada (hardcodeada) dentro de la imagen?
La imagen oficial de Nginx en Alpine soporta plantillas en /etc/nginx/templates/default.conf.template. Configuramos ENV NGINX_ENVSUBST_FILTER="BACKEND_URL" para que al arrancar el contenedor reemplace ${BACKEND_URL} por el valor inyectado desde el ConfigMap de Kubernetes (http://ott-backend:5000).
12. ¿Cómo manejan las contraseñas de los usuarios y las credenciales de conexión a PostgreSQL?
En la base de datos nunca guardamos contraseñas en texto plano; almacenamos únicamente el hash generado por bcrypt con salt aleatorio (por ejemplo $2b$12$...). Y las credenciales de conexión a PostgreSQL se inyectan al contenedor mediante el objeto Secret ott-secrets de Kubernetes usando secretKeyRef.

Preguntas para Sebastián (Kubernetes, Minikube y Observabilidad - D4, D8)

13. ¿Por qué usaron un StatefulSet para PostgreSQL (ott-db) y Deployment para Backend y Frontend?
Porque Frontend y Backend son servicios sin estado (stateless): sus pods son intercambiables con nombres aleatorios. En cambio, PostgreSQL es un servicio con estado (stateful) que requiere identidad de red predecible (ott-db-0) y asociación estable con su volumen de almacenamiento persistente (postgres-pvc).
14. ¿Cuál es la diferencia entre readinessProbe y livenessProbe en 04-backend.yaml?
La readinessProbe le indica al Service de Kubernetes cuándo el pod está listo para recibir tráfico (si falla, lo saca temporalmente de los endpoints del Service sin matarlo). La livenessProbe verifica si el proceso sigue sano; si falla reiteradamente, Kubernetes reinicia el contenedor automáticamente (self-healing).
15. ¿Qué pasa con los usuarios nuevos o los favoritos guardados si se reinicia el pod ott-db-0?
Se conservan intactos porque el directorio de datos de PostgreSQL (/var/lib/postgresql/data) está montado sobre el PersistentVolumeClaim postgres-pvc respaldado por el PersistentVolume postgres-pv en el nodo de Minikube, cuyo ciclo de vida es independiente del pod.
16. ¿Por qué definieron resources.requests y resources.limits en los pods?
Los requests le garantizan al scheduler de Kubernetes cuánta CPU y memoria mínima necesita reservar para programar el pod, mientras que los limits evitan que una fuga de memoria o pico de CPU en un contenedor agote los recursos del nodo de Minikube y afecte a los demás servicios.
