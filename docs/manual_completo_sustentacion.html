Módulo 01 · Comprensión del Sistema

Visión Global y Recorrido de una Petición

Antes de aprender comandos individuales, todo el equipo debe comprender cómo funciona el producto y cómo viaja una solicitud a través de las tres capas desplegadas en Kubernetes.

01 · Entrada (Puerto 80 / 30080)

Capa Frontend · Nginx

Cuando un usuario entra desde su navegador, la petición llega primero al pod ott-frontend que ejecuta Nginx 1.25 Alpine.

  • Si pide un archivo estático (como /static/videos/monos.mp4, un póster o el archivo style.css), Nginx lo lee directamente de su propio disco y lo entrega al navegador aplicando caché de 30 días.
  • Si pide una ruta dinámica (como /auth/login, /home/, /api/movies o /apidocs/), Nginx actúa como Reverse Proxy y reenvía la solicitud por la red interna del clúster hacia http://ott-backend:5000.
02 · Procesamiento (Puerto 5000)

Capa Backend · Flask MVC

El pod ott-backend ejecuta Python 3.11 con Flask 3.1.1 bajo una arquitectura Modelo-Vista-Controlador.

  • Controladores (Blueprints): Reciben la petición HTTP, verifican la cookie de sesión firmada con SECRET_KEY y delegan la operación a la capa de servicios.
  • Servicios: Ejecutan la lógica de negocio (validación de contraseñas con bcrypt, filtrado por región del usuario, cálculo de likes) y abren conexiones SQL hacia ott-db:5432 mediante psycopg2.
  • Respuesta: Renderiza una vista HTML con Jinja2 o devuelve un objeto JSON (en las rutas /api/*).
03 · Almacenamiento (Puerto 5432)

Capa de Datos · PostgreSQL 16

El pod ott-db-0 ejecuta PostgreSQL 16 Alpine como un StatefulSet en Kubernetes.

  • Inicialización automática: Al arrancar por primera vez, ejecuta el script init.sql montado desde un ConfigMap, creando las 6 tablas relacionales y sembrando 2 usuarios y 20 películas.
  • Persistencia en disco: Sus archivos de datos residen en el volumen persistente postgres-pvc (1 GiB), garantizando que los registros sobrevivan aunque el contenedor se reinicie.

Ubicación: OTT-/frontend/

1. Carpeta frontend/

Función principal: Recibir las peticiones HTTP de los usuarios en el puerto 80, servir directamente los archivos multimedia pesados desde disco y redirigir las rutas de la aplicación hacia Flask.

  • Dockerfile: Parte de nginx:1.25-alpine. Define ENV BACKEND_URL=http://backend:5000 y ENV NGINX_ENVSUBST_FILTER="BACKEND_URL" para que al arrancar el contenedor reemplace dinámicamente la URL del backend según el entorno (Docker Compose o Kubernetes).
  • nginx.conf.template: Configura client_max_body_size 50M; y divide las rutas en dos bloques:
    • location /static/: Sirve /usr/share/nginx/html/static/ con expires 30d;.
    • location /: Hace proxy_pass ${BACKEND_URL}; propagando las cabeceras HTTP originales del cliente.
  • static/: Contiene el diseño monocromático en css/style.css, el reproductor con guardado periódico en js/player.js, los pósters en images/posters/ y los 20 videos en videos/*.mp4.
Ubicación: OTT-/backend/

2. Carpeta backend/

Función principal: Implementar la lógica de negocio bajo arquitectura MVC, gestionar la seguridad de sesiones y exponer la API REST documentada con OpenAPI.

  • app.py: Configura la clave de sesión app.secret_key, inicializa Swagger en /apidocs/ y registra los 6 Blueprints.
  • config/db_config.py: Lee DATABASE_URL del entorno y retorna conexiones PostgreSQL usando RealDictCursor (para acceder a las columnas por nombre).
  • models/movie.py: Define la entidad Movie y su método from_dict(), encargado de normalizar rutas de pósters y asignar imagen de respaldo al banner principal (hero_url).
  • controllers/api_controller.py: Expone los endpoints JSON puros:
    • GET /api/health: Ejecuta SELECT 1 AS test; en PostgreSQL y retorna 200 OK ({"database": "connected", "status": "ok"}) o 500 si falla la conexión.
    • GET /api/movies y GET /api/movies/<id>: Retornan el catálogo o un error controlado 404 si el ID no existe.
  • services/: Separa el SQL de los controladores: auth_service.py cifra y verifica contraseñas con bcrypt; watch_history_service.py hace INSERT ... ON CONFLICT DO UPDATE del segundo de reproducción.
Ubicación: OTT-/database/

3. Carpeta database/

Función principal: Definir la estructura relacional en PostgreSQL y poblar los datos iniciales automáticamente.

  • init.sql: Define 6 tablas relacionales con borrado en cascada (ON DELETE CASCADE):
    1. users: id, email UNIQUE, password_hash, created_at.
    2. profiles: id (FK users), nombre, region, suscripcion.
    3. movies: id, titulo, descripcion, categoria, region, video_url, imagen_url, hero_url, tipo.
    4. favorites: Relación única UNIQUE(usuario_id, pelicula_id) para Mi Lista.
    5. watch_history: Guarda el minuto exacto por UNIQUE(usuario_id, pelicula_id).
    6. ratings: Guarda la calificación (1 Like, -1 Dislike) por usuario y película.
  • Semillas precargadas: Crea los usuarios admin@ott.com (admin123) y demo@ott.com (demo123) junto con las 20 producciones del catálogo.
Ubicación: OTT-/tests/

4. Carpeta tests/

Función principal: Validar de forma automatizada las reglas de negocio, la integración con PostgreSQL y el flujo en navegador real.

  • test_unit.py (10 pruebas): Verifica instanciación de Movie, normalización de rutas antiguas, hashing y validación con bcrypt, filtrado por región (LATAM y GLOBAL), filtro de Cine Colombiano y códigos de respuesta HTTP de login, registro, Swagger y API.
  • test_flow.py (4 pruebas): Prueba la comunicación real entre Flask y PostgreSQL: estado conectado en /api/health, lectura de las 20 películas semilla, autenticación de demo@ott.com contra la tabla users y navegación con sesión activa.
  • test_e2e_playwright.py (6 pruebas): Lanza un navegador Chromium headless y prueba visualmente el formulario de login, el rechazo de credenciales inválidas, el login exitoso hacia /home/, el reproductor en /movie/1, el buscador /movie/search?q=Monos y la carga de Swagger UI.

Módulo 03 · Infraestructura y Entrega Continua

Cómo funcionan CI/CD, Docker y Kubernetes en CINÉFILO

Conceptos esenciales que explican cómo el código pasa de un commit en Git a ejecutarse con alta disponibilidad dentro del clúster de Minikube.

Archivo: .github/workflows/ci-cd.yml

1. Pipeline CI/CD y Control de Fallos

El workflow de GitHub Actions se ejecuta automáticamente en cada push o pull_request hacia la rama main y consta de dos Jobs secuenciales:

  • Job 1 (unit-and-integration-tests): Crea un contenedor de servicio postgres:16-alpine en el runner de Ubuntu, ejecuta database/init.sql y corre las 10 pruebas unitarias y las 4 pruebas de flujo SQL.
  • Compuerta de Control de Fallos: El Job 2 incluye needs: unit-and-integration-tests e if: success(). Si una sola prueba falla en el Job 1, el pipeline se detiene inmediatamente y bloquea la creación de imágenes Docker.
  • Job 2 (docker-build-and-traceability): Extrae el hash corto del commit (git rev-parse --short HEAD), construye las imágenes con tres tags (v1.0.0, sha-<commit> y latest), valida con un script en Python todos los archivos YAML de k8s/, comprueba con grep que los manifiestos apunten a v1.0.0 y genera una tabla de trazabilidad en el Job Summary.
Ubicación: OTT-/k8s/ (01 al 05)

2. Los 5 Manifiestos de Kubernetes Explicados

  • 01-namespace.yaml: Crea el namespace ott-platform para aislar todos los objetos del proyecto dentro del clúster.
  • 02-configmap-and-secret.yaml: Separa las variables públicas en el ConfigMap ott-config, almacena las credenciales en Base64 dentro del Secret ott-secrets y guarda el script init.sql en el ConfigMap ott-db-init.
  • 03-postgres.yaml: Declara un PersistentVolume y un PersistentVolumeClaim (postgres-pvc de 1 GiB). Despliega PostgreSQL como un StatefulSet (ott-db) porque requiere identidad estable (ott-db-0) y almacenamiento persistente, exponiéndolo internamente con un Service ClusterIP en el puerto 5432.
  • 04-backend.yaml: Despliega Flask como un Deployment stateless con límites de CPU/RAM y sondas readinessProbe y livenessProbe que consultan GET /api/health:5000.
  • 05-frontend.yaml: Despliega Nginx como un Deployment y lo publica mediante un Service NodePort (80:30080).

Módulo 05 · Defensa Técnica y Preparación

Preguntas de Evaluación y Protocolo de Contingencia

Respuestas precisas a las preguntas frecuentes de sustentación y comandos de preparación rápida antes de iniciar.

Pregunta Técnica Respuesta Precisa Basada en la Implementación
1. ¿Por qué desacoplaron Nginx en el contenedor ott-frontend en lugar de servir todo desde Flask? Porque el catálogo incluye 20 archivos de video MP4. Servir flujos binarios de video desde el servidor de desarrollo de Flask bloquea los hilos de Python. Nginx entrega directamente todo el directorio /static/ desde disco con encabezados de caché de 30 días y actúa como proxy inverso únicamente para las rutas dinámicas.
2. ¿Cómo garantizan en GitHub Actions que las pruebas de integración sean reales y que un fallo detenga la entrega? El Job 1 aprovisiona un contenedor de servicio postgres:16-alpine, inyecta database/init.sql y ejecuta las pruebas contra esa base de datos real. El Job 2 depende del primero mediante needs: unit-and-integration-tests e if: success(), bloqueando la construcción de imágenes si falla cualquier test.
3. ¿Por qué PostgreSQL se despliega como StatefulSet mientras Flask y Nginx usan Deployment? Flask y Nginx son componentes stateless (sin estado local), por lo que sus pods son efímeros e intercambiables. PostgreSQL es stateful y requiere identidad de red predecible (ott-db-0) y asociación estable con el reclamo de volumen persistente postgres-pvc.
4. ¿Cuál es la diferencia operativa entre la readinessProbe y la livenessProbe que configuraron hacia /api/health? La readinessProbe determina cuándo el pod puede recibir tráfico del Service (si la base de datos aún no responde, retira el pod temporalmente sin reiniciarlo). La livenessProbe detecta bloqueos fatales y ordena a Kubernetes reiniciar el contenedor automáticamente.
5. ¿Cómo inicializa PostgreSQL las tablas dentro de Kubernetes sin montar carpetas locales de Windows? Empaquetamos el contenido de database/init.sql dentro del ConfigMap ott-db-init y lo montamos como archivo en /docker-entrypoint-initdb.d/init.sql dentro del pod ott-db-0. Así el clúster es portable en cualquier sistema operativo o entorno como GitHub Codespaces.
6. ¿Cómo se diferencia el proceso de CI del despliegue declarativo / GitOps en su proyecto? La CI en GitHub Actions valida el código, ejecuta pruebas y produce artefactos inmutables etiquetados con versión y SHA. Los manifiestos en la carpeta k8s/ del repositorio constituyen la fuente única de verdad del estado deseado del clúster, que reconciliamos sobre Minikube con kubectl apply -f k8s/.
