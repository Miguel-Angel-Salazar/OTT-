🎬 1. ¿En qué consiste el proyecto y cómo funciona por dentro?

Lo primero que los 4 integrantes deben tener claro antes de pasar al frente.

¿Qué es CINÉFILO?

Es una plataforma web de películas y series estilo MUBI (con foco especial en Cine Colombiano e independiente). Permite registrarse, iniciar sesión, ver un catálogo filtrado según la región del usuario, reproducir trailers/películas en video MP4 guardando el segundo exacto donde el usuario quedó, agregar películas a Mi Lista (favoritos), dar Like/Dislike y buscar por título o género.

¿Cuáles son sus 3 piezas (Contenedores / Pods)?

  1. Frontend (Nginx - Puerto 80): Es la puerta de entrada. Entrega rápido las imágenes, el CSS y los 20 videos MP4, y si el usuario pide una página o dato, se lo pide al Backend.
  2. Backend (Python Flask - Puerto 5000): Es el cerebro. Valida usuarios, procesa favoritos/progreso, expone la API y Swagger (/apidocs/) y se conecta a la base de datos.
  3. Base de Datos (PostgreSQL 16 - Puerto 5432): Guarda en 6 tablas los usuarios, perfiles, las 20 películas, favoritos, likes e historial de reproducción.

¿Cómo nos evalúa el profesor según el Excel?

  • Parte I · Elevator Pitch (20% · 4 a 5 min): Explicar el problema, el valor de la plataforma y por qué usamos Docker, CI y Kubernetes (Diapositivas 2 a 5).
  • Parte II · Demo Técnica en Vivo (80% · 15 min): Mostrar en vivo Git, GitHub Actions, Docker Hub, Minikube corriendo, la página web funcionando y qué pasa cuando un pod se cae.
  • Regla de oro del Excel: Nunca mostrar contraseñas en texto plano en pantalla.

📂 2. ¿Dónde están las carpetas del proyecto, qué tienen adentro y para qué sirven?

Todo el proyecto está en la carpeta raíz OTT-/. Aquí tienes exactamente qué hay dentro de cada carpeta por si el profesor pide abrir cualquiera de ellas.

📍 Ruta: OTT-/frontend/

1. Carpeta frontend/ (Servidor Web Nginx y Archivos Multimedia)

¿En qué consiste? Es la capa que recibe todas las visitas del navegador en el puerto 80. Usa Nginx 1.25 Alpine para dos cosas: entregar directamente los archivos pesados (videos MP4 y pósters) con memoria caché, y actuar como Reverse Proxy (puente) enviando las peticiones de inicio de sesión o catálogo hacia el Backend Flask.

¿Qué archivos tiene adentro?

  • Dockerfile: Instrucciones para crear la imagen Docker del frontend sobre nginx:1.25-alpine.
  • nginx.conf.template: Configuración de Nginx. Tiene dos reglas clave:
    • location /static/: Entrega fotos, estilos CSS, JS y videos directamente desde el disco sin molestar a Python.
    • location /: Redirige todo lo demás hacia ${BACKEND_URL} (que apunta a http://ott-backend:5000).
  • static/: Contiene 4 subcarpetas: css/ (estilos), js/ (lógica del reproductor de video), images/posters/ (las 20 carátulas) y videos/ (los 20 archivos de video .mp4 como monos.mp4, roma.mp4, etc.).
📍 Ruta: OTT-/backend/

2. Carpeta backend/ (Aplicación Python Flask MVC + API Swagger)

¿En qué consiste? Es el servidor de aplicaciones escrito en Python 3.11 con Flask 3.1.1 siguiendo el patrón Modelo-Vista-Controlador (MVC). Corre en el puerto 5000.

¿Qué archivos y subcarpetas tiene adentro?

  • app.py: Archivo principal que arranca Flask, configura Swagger UI en /apidocs/ y conecta todos los módulos (Blueprints).
  • Dockerfile: Construye la imagen del backend sobre python:3.11-slim, instala requirements.txt, crea un usuario seguro sin permisos de administrador (USER appuser) y define el HEALTHCHECK hacia /api/health.
  • config/db_config.py: Lee la variable DATABASE_URL y abre la conexión hacia PostgreSQL usando la librería psycopg2.
  • models/movie.py: Define la clase Movie y arregla automáticamente las rutas de las imágenes.
  • controllers/: Reciben las peticiones web:
    • api_controller.py: Tiene los endpoints JSON: GET /api/health (verifica si la BD responde), GET /api/movies y GET /api/movies/<id>.
    • auth_controller.py: Login y registro de usuarios.
    • home_controller.py: Muestra el catálogo principal filtrando por la región del usuario y separa la fila de Cine Colombiano.
    • movie_controller.py: Muestra el reproductor, el buscador (/movie/search), los Likes/Dislikes y guarda el segundo del video (POST /movie/<id>/progreso).
    • favorite_controller.py y profile_controller.py: Manejan Mi Lista y el cambio de plan (Básica/Premium).
  • services/: Contienen las consultas SQL reales hacia PostgreSQL y el cifrado de contraseñas con bcrypt (auth_service.py).
  • templates/: Las plantillas HTML (Jinja2) de login, catálogo, reproductor y perfil.
📍 Ruta: OTT-/database/

3. Carpeta database/ (Esquema SQL y Datos Semilla)

¿En qué consiste? Contiene el script que crea automáticamente la base de datos propia en PostgreSQL 16 cuando el contenedor o el pod arranca por primera vez, eliminando cualquier dependencia de Supabase.

¿Qué tiene adentro?

  • init.sql: Crea las 6 tablas relacionales con llaves foráneas:
    1. users: Guarda el correo y el hash seguro de la contraseña en bcrypt.
    2. profiles: Nombre del usuario, región (LATAM, EUROPA, USA) y plan (Basica o Premium).
    3. movies: Las 20 películas y series con título, sinopsis, categoría, región y rutas de póster y video MP4.
    4. favorites: Qué películas tiene cada usuario en Mi Lista.
    5. watch_history: En qué segundo/minuto quedó viendo cada película cada usuario.
    6. ratings: Los Likes (1) y Dislikes (-1).
    Además, inserta automáticamente 2 cuentas listas para probar: demo@ott.com (clave demo123) y admin@ott.com (clave admin123).
📍 Ruta: OTT-/tests/

4. Carpeta tests/ (Las 20 Pruebas Automatizadas)

¿En qué consiste? Contiene las 20 pruebas que garantizan que el código, la base de datos y la interfaz web funcionen sin errores.

¿Qué hace cada uno de los 3 archivos?

  • test_unit.py (10 pruebas unitarias): Prueba que la clase Movie funcione bien, que bcrypt encripte y valide contraseñas correctamente, que el filtro por región y el de Cine Colombiano no fallen, y que las rutas básicas (/, /auth/login, /apidocs/, /api/movies) respondan.
  • test_flow.py (4 pruebas de integración con PostgreSQL): Se conecta a la base de datos real y comprueba que /api/health diga connected, que las 20 películas semilla existan en la tabla movies, que el login de demo@ott.com funcione y que pueda navegar al catálogo.
  • test_e2e_playwright.py (6 pruebas de navegador E2E): Abre un navegador Chromium real automático con Playwright, llena el formulario de login con una clave mala (verifica que la rechace), luego inicia sesión con demo@ott.com, entra al reproductor de Monos, usa el buscador y abre Swagger.
📍 Ruta: OTT-/.github/workflows/ci-cd.yml

5. Carpeta .github/workflows/ (Pipeline CI/CD en GitHub Actions)

¿En qué consiste? Es el robot automático de GitHub. Cada vez que alguien sube un cambio (git push o Pull Request a main), ejecuta dos trabajos en orden:

  • Trabajo 1 (unit-and-integration-tests): Crea un contenedor temporal de PostgreSQL 16 en la nube de GitHub, le carga database/init.sql y corre las pruebas de test_unit.py y test_flow.py.
  • Control de Fallos: Si una sola prueba falla en el Trabajo 1, el pipeline se detiene en rojo y prohíbe pasar al Trabajo 2.
  • Trabajo 2 (docker-build-and-traceability): Si todas las pruebas pasaron, construye las imágenes Docker del Backend y Frontend etiquetándolas con la versión v1.0.0 y el código del commit (sha-xxxxxxx), revisa que los 5 archivos de la carpeta k8s/ estén bien escritos, sube las imágenes a Docker Hub y escribe una tabla resumen de trazabilidad.
📍 Ruta: OTT-/k8s/

6. Carpeta k8s/ (Los 5 Manifiestos de Kubernetes para Minikube)

¿En qué consiste? Son los 5 archivos YAML numerados que le dicen a Kubernetes (Minikube) cómo levantar toda la plataforma en el clúster:

  • 01-namespace.yaml: Crea una "burbuja" o espacio propio llamado ott-platform para que nuestros contenedores no se mezclen con otros proyectos.
  • 02-configmap-and-secret.yaml: Crea dos objetos de configuración: ott-config (datos públicos como el puerto 5000 y el nombre de la BD), ott-secrets (las contraseñas ocultas en Base64) y ott-db-init (que le entrega el archivo init.sql a PostgreSQL).
  • 03-postgres.yaml: Crea el disco duro virtual de 1 Gigabyte (postgres-pv y postgres-pvc) para que no se borren los datos, levanta la base de datos como StatefulSet (ott-db) y crea su servicio interno en el puerto 5432.
  • 04-backend.yaml: Levanta el pod de Flask (ott-backend), le conecta las contraseñas desde el Secret, le pone límites de memoria/CPU y configura los chequeos de salud (readinessProbe y livenessProbe) hacia /api/health.
  • 05-frontend.yaml: Levanta el pod de Nginx (ott-frontend) y lo expone hacia afuera mediante un Service NodePort (puerto 30080).

2. Qué decir en el Elevator Pitch (Diapositiva 4 · ~1 min)

«En el criterio P3 justificamos por qué nuestras decisiones técnicas y prácticas DevOps resuelven necesidades reales del producto:

Como compensación (trade-off), empaquetar los videos MP4 de prueba en la imagen del frontend aumenta su peso a ~380 MB, pero a cambio nos da portabilidad inmediata en cualquier clúster sin depender de almacenamiento externo.»

🧠 4. Diccionario Fácil de Conceptos (Para no dudar en ninguna pregunta)

Explicaciones cortas y directas de cada término técnico que usamos en el proyecto.

🔹 Pod vs Contenedor

El contenedor es la aplicación empaquetada (por ejemplo Flask o Nginx). El Pod es la unidad mínima de Kubernetes que envuelve a ese contenedor, dándole una dirección IP propia dentro del clúster.

🔹 Deployment vs StatefulSet

Usamos Deployment para el Frontend y el Backend porque no guardan archivos propios en disco (si se borran y nacen con otro nombre no pasa nada). Usamos StatefulSet para PostgreSQL (ott-db-0) porque una base de datos necesita mantener siempre el mismo nombre y su mismo disco duro conectado.

🔹 Service ClusterIP vs NodePort

Un Service ClusterIP es privado: solo permite comunicación adentro de Minikube (así protegemos la BD en el puerto 5432 y el Backend en el 5000). Un Service NodePort abre un puerto hacia afuera (30080) para que podamos entrar al Frontend Nginx desde el navegador.

🔹 PV y PVC (Persistencia)

El PV (PersistentVolume) es el espacio de disco reservado en el nodo, y el PVC (PersistentVolumeClaim) es el "contrato" con el que el pod de PostgreSQL reclama 1 Gigabyte de ese disco para que las tablas no se borren nunca aunque el pod se reinicie.

🔹 ConfigMap vs Secret

Ambos sirven para pasar variables de entorno a los pods sin escribirlas fijas en los Dockerfiles. En el ConfigMap van datos públicos (como el puerto 5000 o el nombre de la BD), y en el Secret van datos confidenciales codificados en Base64 (como contraseñas y SECRET_KEY).

🔹 ReadinessProbe vs LivenessProbe

Son dos chequeos automáticos que hace Kubernetes llamando a /api/health. La ReadinessProbe avisa cuando el contenedor ya terminó de arrancar y puede recibir usuarios; la LivenessProbe vigila que no se haya quedado bloqueado, y si falla, reinicia el pod solo (Self-Healing).
